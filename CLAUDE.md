# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an STM32F407VET6 microcontroller project using STM32CubeMX for hardware configuration and CMake for building. The project includes:
- STM32F407 HAL (Hardware Abstraction Layer) drivers
- CMSIS (Cortex Microcontroller Software Interface Standard) libraries
- GPIO and other peripheral configurations generated by STM32CubeMX
- OpenOCD debugging support via VS Code

**Target**: STM32F407VET6 (ARM Cortex-M4 with FPU)  
**Configuration Tool**: STM32CubeMX (`.ioc` file)  
**Build System**: CMake with Ninja generator  
**Debugging**: OpenOCD + Cortex-Debug extension in VS Code

**Integrated Modules** (Real Hardware Confirmed):
- 🤖 **DC Brushed Motor** with **TB6612** or **TB6600** driver (dual channel)
  - Max 1.2A per channel, 4.5-13.5V motor supply, 3.3V/5V logic
  - Datasheet: `TB6612FNG Datasheet.pdf`, also encoder variant `MC310` available
- 📡 **MPU6050** 6-axis IMU (I2C)
  - Datasheets: `PS-MPU-6000A.pdf` (register map), `RM-MPU-6000A.pdf` (app notes)
  - I2C Address: 0x68 (default) or 0x69
- 👀 **8-Channel Grayscale Sensor** for line tracking (ADC or GPIO)
  - Datasheet: `亚博智能灰度循迹模块用户入门手册.pdf`
  - 5V supply, 1-3 cm detection distance
- ⚙️ **28BYJ-48 Stepper Motor** with **ULN2003** driver
  - 4-phase unipolar, 5V, 2048 steps/revolution (with gearing)
  - Datasheets: `28BYJ48规格书.doc`, `ULN2003英文数据手册.pdf`

## Build & Development

### Building the Project

Use CMake with one of the provided presets:

```bash
# Configure Debug build
cmake --preset Debug

# Build Debug version
cmake --build build/Debug

# Or configure Release build
cmake --preset Release
cmake --build build/Release
```

The compiled ELF file will be at `build/Debug/F407VET6_Templet.elf` (or `build/Release/` for Release builds).

### Project Structure

- 
  - `Core/Src/gpio.c` - GPIO peripheral initialization (generated by CubeMX)
  - `Core/Src/stm32f4xx_it.c` - Interrupt handlers
  - `Core/Src/stm32f4xx_hal_msp.c` - HAL MSP (Microcontroller Support Package) callbacks
  - `Core/Inc/` - Header files for Core code
  **Core/**: Application and system code
  - `Core/Src/main.c` - Main entry point
- **Drivers/**: STM32 HAL drivers and CMSIS libraries (vendor-supplied, generated by CubeMX)
  - `STM32F4xx_HAL_Driver/` - STM32F4xx Hardware Abstraction Layer
  - `CMSIS/` - ARM CMSIS core and optional libraries (DSP, NN)

- **cmake/**: Build configuration
  - `stm32cubemx/CMakeLists.txt` - Generated sources, symbols, and HAL driver setup
  - `gcc-arm-none-eabi.cmake` - ARM toolchain configuration

- **F407VET6_Templet.ioc** - STM32CubeMX project configuration file

### Adding User Code

- Add application source files to `Core/Src/` and headers to `Core/Inc/`
- Add user-defined source files to the main `CMakeLists.txt` in the `target_sources()` section
- Add include paths in `target_include_directories()`
- Add compiler definitions (macros) in `target_compile_definitions()`

### STM32CubeMX Workflow

If you modify `F407VET6_Templet.ioc` with STM32CubeMX:
1. CubeMX regenerates code in `Core/` and `cmake/stm32cubemx/`
2. Preserve user code by placing it between `/* USER CODE BEGIN ... */` and `/* USER CODE END ... */` markers
3. Re-run CMake configure after regeneration

## Code Organization

### USER CODE Sections

STM32CubeMX-generated files use special markers to protect user code:

```c
/* USER CODE BEGIN ... */
// Your code here - preserved during regeneration
/* USER CODE END ... */
```

Always place custom code within these sections in generated files (`main.c`, `gpio.c`, etc.). Code outside these sections will be overwritten on regeneration.

### Custom Application Code

Create new `.c` and `.h` files in `Core/Src/` and `Core/Inc/` for your application logic. These files are not regenerated by CubeMX and are fully under your control.

## Embedded Development Standards

### HAL Library Integration

**Initialization Order** (enforced in generated `main.c`):
1. `MX_GPIO_Init()` - GPIO peripheral setup
2. `MX_<PERIPHERAL>_Init()` - UART, SPI, I2C, ADC, etc.
3. `HAL_NVIC_EnableIRQ()` - Interrupt handlers after all peripherals initialized

**Critical Rules**:
- Always check HAL return values: `if (HAL_<Function>(...) != HAL_OK) Error_Handler();`
- Place interrupt callbacks in `Core/Src/stm32f4xx_it.c` between `USER CODE` markers
- Interrupt service routines must be **fast** — set flags, let main program handle logic
- Use `volatile` for variables shared between ISR and main program

### Memory Safety

**Stack vs Heap**:
- Avoid dynamic allocation (`malloc`/`free`) — use static arrays or stack allocation
- Never call memory functions inside interrupt handlers
- Carefully estimate stack depth; embedded systems have small stacks (~2KB typical)

**DMA Buffers**:
- Must be **global or static** — never allocate on stack
- Example: `static uint8_t dma_buffer[256];` not `uint8_t buffer[256];` on stack

**Common Pitfalls**:
- Stack overflow → random behavior, hard to debug
- Calling `HAL_Delay()` in ISR → system lockup
- Ignoring HAL return codes → silent failures
- DMA buffer on stack → data corruption

### Interrupt Handling

**Safe Pattern**:
```c
// In stm32f4xx_it.c
volatile uint8_t flag = 0;

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
    if (huart->Instance == USART1) {
        flag = 1;  // Set flag, return immediately
    }
}

// In main.c
while (1) {
    if (flag) {
        flag = 0;
        process_data();  // Do actual work here
    }
}
```

**Dangerous Pattern** (avoid):
```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
    HAL_Delay(100);           // ❌ Blocking in ISR
    process_complex_data();    // ❌ Long operation in ISR
    HAL_UART_Transmit(...);   // ❌ May deadlock
}
```

### STM32CubeMX Workflow

**Code Protection**:
- All user code must be within `/* USER CODE BEGIN/END */` markers
- Code outside these sections is **overwritten** on regeneration
- Create new `.c`/`.h` files in `Core/Src/Inc` for custom modules (not regenerated)

**After Modifying `.ioc` File**:
1. Regenerate with CubeMX
2. CMake will recompile automatically
3. Review generated `cmake/stm32cubemx/CMakeLists.txt` for new files

### Peripheral Configuration Notes

**UART (Serial Communication)**:
- Prefer DMA mode for high-speed or continuous data
- Polling mode only for initialization/low-speed
- Set appropriate baud rate (default 115200 typical)
- Use correct flow control pins if needed (RTS/CTS)

**SPI/I2C (Synchronized Buses)**:
- Check device ready before operations: `HAL_I2C_IsDeviceReady()`
- Set timeouts appropriately for your bus speed
- SPI: Verify MOSI/MISO/CLK/CS pin configuration

**GPIO**:
- Use CubeMX for pin configuration, not direct register access
- Input pullup/pulldown configured in CubeMX
- Output speed (`GPIO_SPEED_FREQ_LOW/HIGH`) affects power and EMI

### Debugging with OpenOCD

**Hardware Setup**:
- ST-Link or CMSIS-DAP debugger connected to SWD pins (SWCLK, SWDIO, GND)
- Launch config in `.vscode/launch.json` points to OpenOCD
- GDB connected on localhost:3333 (default)

**Debugging Commands**:
- Set breakpoints: Click line number in VS Code or `break main` in GDB
- Step: F10 (step over), F11 (step into)
- Continue: F5
- Watch variables: Right-click variable → "Add to Watch"
- Inspect registers: `.gdbinit` configuration or GDB `info registers`

### Performance Optimization

**Power Consumption**:
- Disable unused peripheral clocks: `__HAL_RCC_<MODULE>_CLK_DISABLE()`
- Use sleep/stop modes for idle periods
- Set GPIO to low-power mode when not active

**Execution Speed**:
- Critical sections can use inline functions or macros
- Avoid floating-point in tight loops (use fixed-point if precision allows)
- Loop unrolling for data-intensive operations
- Optimize for your target frequency (168 MHz for F407)

### Best Practices for This Project

1. **Edit user code only** — in `Core/Src/*.c` or new files in `Core/`, never touch `Drivers/`
2. **Regenerate periodically** — when modifying `.ioc` file or adding peripherals
3. **Test on hardware** — emulation catches most but not all issues (timing, hardware quirks)
4. **Use breakpoints** — easier than logging for debugging hardware interactions
5. **Check return codes** — every HAL call can fail; `if (status != HAL_OK)` is non-negotiable
